# Coverity re-deployed from data center to cloud

This scenario re-deploys Coverity from a data center to a Kubernetes cluster in the
cloud. The following steps outline the re-deployment process:

Important: These are Administrator procedures.

Table 1. Coverity re-deployed from data center to cloud

| Step | Description | Refer to |
| --- | --- | --- |
| 1 | Request access to Black Duck Community. | - Request access to Black Duck Community |
| 2 | Request a node-unlocked license for Coverity Connect from Black Duck Support. | - Obtain your Coverity licenses |
| 3 | Request Black Duck Docker registry credentials from Black Duck Support. | - Request Black Duck Docker registry credentials |
| 4 | Download the Helm chart from the Black Duck public Docker registry. | - Downloading the Helm chart from the Black Duck public Docker registry |
| 5 | Download any required open-source images. | - Open source container images |
| 6 | Manage container images. You can find this information within a single chapter.  You must either:   - Preferred method: Create and set up your own private image   registry. If you create a registry, you must pull, tag and push   images to your registry. - Alternate method: Set up the Helm chart to download images   directly from the Black Duck private registry during   deployment.   This chapter also describes the following relevant information:   - Introduces how Kubernetes manages container images  Lists of available container images and their purpose. - Describes how to create container image pull secrets. - How to configure the Helm chart for image access and   download. | - Managing container images |
| 7 | Download analysis client toolkit files and other files as needed from the Black Duck private Docker registry:   - If you are deploying Scan Service to perform analyses in   Kubernetes, you must download a Coverity toolkit tar file for   each analysis version that will be used to perform   analyses. Note: You will upload this   file to Connect after you deploy Coverity as described in   Uploading Coverity Tools artifacts to the Connect UI. - Set the NGINX `proxy-body-size` to ba able to   upload the Coverity toolkit tar file to Connect. - If you are NOT deploying Scan Service in Kubernetes, you must   download a full Coverity Analysis client file for the version   that will be used to perform local analyses. - Download platform files, host ID files, and documentation files   as needed. | - Coverity client installer and documentation files - Set NGINX proxy-body-size for Coverity toolkit tar file upload to Connect - Downloading a full analysis client file from the Black Duck repository - Downloading platform, host ID, and documentation files from the Black Duck registry using curl |
| 8 | Infrastructure and configuration:   - Install required software. - Configure access privileges. - Create a Kubernetes cluster. - Expose the Kubernetes cluster. - Create a Kubernetes namespace. - Create or migrate a PostgreSQL database instance for each   instance of Coverity Connect. - Planning: Size the PostgreSQL pod resources. - Planning: Size Connect `cim` pod resources. - Configure Kubernetes logging.   You can set up the Kubernetes infrastructure either on-prem or in a provisioned cloud environment. If on-prem, you will need to obtain, install, and manage all components of the environment.  If you deploy Coverity Connect in the cloud, the cloud provider can provide and maintain Kubernetes as a provisioned service.  Platform-specific infrastructure and configuration:   - General/on-prem: - Amazon AWS - Google GCP - Microsoft Azure - Red Hat OpenShift   ARM64:   - If the cluster will use ARM64, create the ARM64 cluster, node   pools and tolerations. | Infrastructure prerequisites:   - Install required software - Access privileges - Create a Kubernetes cluster - Expose the Kubernetes cluster - Create a Kubernetes namespace - PostgreSQL databases and PostgreSQL pod - Sizing PostgreSQL pod resources - Sizing a Coverity Connect (cim) pod for optimum performance - Configure Kubernetes logging   Platform-specific infrastructure and configuration:   - General/on-prem: Infrastructure and configuration - AWS only: Amazon AWS infrastructure and configuration - GCP only: Google GCP infrastructure and configuration - Azure only: Microsoft Azure infrastructure and configuration - Red Hat OpenShift, including OpenShift routing: Red Hat OpenShift infrastructure and configuration   ARM64:   - Setting up ARM64 support |
| 9 | If not already done, create Scan Service storage and configure Scan Service access privileges to the storage resources.   - For Amazon AWS with an S3 Express storage bucket, set the IAM   policy. - For Amazon AWS with an S3 storage bucket, set the IAM   policy - For Google GCP, the minimum storage bucket permission must be   `storage.buckets.update` which is within   the `roles/storage.legacyBucketOwner`   role. - For Microsoft Azure, the minimum storage blob permission must   be `Storage Blob Data Contributor`. This role   allows users to manage and read/write data to the storage   account. | - For Amazon S3 Express, see AWS: Create S3 Express bucket IAM policies - For Amazon S3, see Specifying AWS S3 storage bucket and cache bucket IAM policy. - For Google GCP, see Google GCP administrator privileges/roles. - For Microsoft Azure, see Microsoft Azure administrator privileges/roles. |
| 10 | Create all access secrets as needed.   - Container image pull secret - Scan tool synchronization secret - Kubernetes ingress TLS secret - Connect license secret - Create a truststore for the Coverity Connect instance. - Create a secure Connect Web application administator   password. Important: When   you deploy Connect for the first time, we highly recommend   that you create a secure password for future administrator   access to the Connect Web application. If you do not create   a password, to re-connect to the web app as administrator,   you will need to manually create a password secret or   contact Black Duck Software for the default password.  Important: You must   also specify the name of the password secret in the   `cim.cimweb.adminPasswordSecret:` Helm   key. - If you are deploying Scan Service, create a Scan Service license   secret, and as needed, an AWS, Azure, or GCS service account   secret. - If you are deploying Cache Service, create a Cache Service CA   certificate secret for Redis. - If you are deploying Cache Service on Azure, create an Azure   Cache Service secret. | Create TLS certificate, keystore, and secrets   - Create a container image pull secret - Create a scan tool synchronization secret - Create a Kubernetes ingress TLS secret - Create a Connect license secret - Creating a truststore ConfigMap for a Connect instance - Managing the Connect Web application administator password - Create a Scan Service license secret - Create a Cache Service CA certificate secret for Redis - Create an Azure Cache Service secret |
| 11 | Prepare a .yaml file containing the following Helm key overrides for the Coverity Connect deployment.  Connect:   - Set the private image registry. - Enable Connect. - Specify the name of the Connect license secret. - Set up PostgreSQL users and permissions. - Specify the Connect Web URL. - Set up PostgreSQL SSL and TLS. - Set up TLS forward proxy.   Scan Services:   - Enable the `scan-services` Helm subchart.. - Prepare the OCI pnPrem MinIO and Redis keys. - Optional: If you are installing Cache Service, prepare the Cache   Service keys.   The following are optional:   - Optional: If you need to enable and use metrics, set the metrics   keys and all other metrics configuration requirements. - Optional: Prepare `cimweb` keys. - Optional: Specify the Connect Web application administator   password secret. - Optional: You can optionally deploy Connect Web application high   availability (HA). - Optional: If you are deploying PostgreSQL database read   replicas, create the replica databases and configure the Helm   keys as needed. | Preparing Helm keys to deploy Coverity   - imageRegistry keys - Enable Connect - Specify the name of the Connect license secret - Create PostgreSQL database access credentials - Specify the Coverity Connect Web URL - Select the PostgreSQL sslmode and find the PostgreSQL root certificate for TLS - Configuring TLS forward proxy   Scan Services:   - Enabling the scan-services Helm subchart - Setting up onPrem OCI Redis, MinIO, and PostgreSQL for Scan Service - Scan Service caching   The following are optional:   - Optional: Metrics - Optional: Preparing cim.cimweb Helm keys - Optional: Set the cim.cimweb.adminPasswordSecret Helm key - Optional: Connect Web application high availability - Optional: Using PostgreSQL read replicas and Pgpool to balance database loads |
| 12 | - Configure pod and container security. | - Configuring pod and container security |
| 13 | - Create scan nodes and schedule scan jobs. | - Creating scan job node pools and scheduling scan jobs |
| 14 | - Configure TLS forward proxy. | - Configuring TLS forward proxy |
| 15 | - Set up onPrem OCI Redis and Minio for scan services. | - Setting up onPrem OCI Redis, MinIO, and PostgreSQL for Scan Service |
| 16 | If you are providing one or more Coverity full analysis kits for programmers to perform local analyses, build a full analysis kit and configure the Helm chart to automatically upload the kit to Connect during deployment. | - Building a full analysis kit and automatically uploading the kit to Connect during deployment |
| 17 | If you are deploying AI-Assisted Triage Plug-in, configure Helm keys and perform the deployment.  Important: AI-Assisted Triage Plug-in is a Beta release feature. | - Deploying the AI-Assisted Triage Plug-in |
| 18 | Run Helm to install Coverity Connect and optionally Scan Service in the Kubernetes cluster. | - Installing chart releases for your deployment |
| 19 | Complete any post-install tasks, including the following:   - Obtain the Coverity Connect URL and login to the Coverity   Connect UI. - Configure SAML using the Coverity Connect UI. - Configure other tools or protocols as needed. | - Post installation or upgrade tasks - Accessing the Connect UI - Configuring SAML |
| 20 | Verify the Coverity cloud deployment. | - Verifying the Coverity cloud deployment |
| 21 | For analysis in the cloud: Set up Thin Client versions in the Connect UI. | - Managing supported Coverity Tools and Thin Client versions in the Connect UI |
| 22 | For local analysis: Create a full Coverity Analysis client image which enables end users can download and install on their client system to perform a local analysis. | - Building a full analysis kit and automatically uploading the kit to Connect during deployment |
| 23 | Migrate the existing database to the cloud. | - Migrating a PostgreSQL database instance to the cloud |
| 24 | Optional: If you deployed or need to deploy multiple replicas of the Connect web application for **web app HA**, manage the HA deployment. | - Connect Web application high availability |
| 25 | End users (programmers): For local analysis: Install the full Coverity Analysis client from the Connect UI Downloads page. | - See the section, Installing Coverity Analysis for local   analysis in the Coverity 2026.6.0 Installation and Upgrade Guide. |
| 26 | End users (programmers): For analysis in the cloud: If Scan Service is installed, to perform an analysis in the cloud, end users must install the appropriate Thin Client version on their client system.  Note: If analyses are performed through a pipeline, the pipeline must be set up. | - Installing Coverity Thin Client on a client system |
| 27 | End users (programmers) can prepare for and perform analyses. | - What is next? preparing and performing analyses |
