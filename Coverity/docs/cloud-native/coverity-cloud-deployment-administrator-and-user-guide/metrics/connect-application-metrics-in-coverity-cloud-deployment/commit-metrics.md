# Commit metrics

The following table describes metrics that deal with the Commit Service and can be used
to assess the health and performance of Coverity Connect commits.

Table 1. Commit metrics

| Metric | Description | Metric type | Examples: PromQL queries |
| --- | --- | --- | --- |
| `connect_active_​commit_count` | **Active commits**  The number of commit jobs currently active in Connect.  The `connect_active_​commit_count` metric is the number of commits currently active and in progress in Connect. The maximum number of active commits is between 0 (no commits in progress) and the number of commit executors or workers as defined by the `cim.properties` parameter `commitPoolThreads`. This together with the commit queue indicates how busy the server is with commits. | Gauge | `connect_active_commit_​count​{kubernetes_​namespace=~"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for `namespace` instances. |
| **Interpreting the metric**  In an ideal system, active commits average 50-75% of the executor size during the active server time, as defined by `commitPoolThreads`. If the average number of active commits is less than half of the executor size, the server might be underutilized.  If active commits are frequently and for sustained periods of time at the max executor size, the system is overutilized. If resources allow, migrate some projects to a server with available resources to better spread the load.  If commit queue is not zero and active commits is less than the maximum executor size, some streams might be locked with commits queued waiting. Look at the stream lock metrics.  If the commit queue is greater than zero and active commits is zero, there is an issue with the queue. Check the logs. | | |
| `connect_commit_​error_​histogram_​count` | **Commit error count**  The `connect_commit_​error_​histogram_​count` metric is a counter that indicates a running count of the number of commit errors since the last Connect start-up. | Histogram counter | `connect_commit_error_​histogram_​count` The `connect_commit_error_​histogram_​count` count metric is derived from the `connect_commit_error_​histogram` metric which is of type Histogram. |
| **Interpreting the metric**  Ideally this number should be zero, static, and flat. A high error rate (high slope) indicates an issue. Areas to look at include:   - if the queue is at or beyond capacity - the Connect HTTP Status Codes - the Connect HTTP Errors Count - the Connect HTTP Request Latency - CPU and memory usage   **Log entries**  Each time an event occurs that increments the metric count, a log entry is created, specifying the event status. | | |
| `connect_commit_​executor_size` | **Commit executors** The current commit executor size.  The `connect_commit_​executor_size` metric is a static parameter that indicates the maximum cores/threads available to the system to execute commits. This parameter matches what is configured in the `cim.properties` `commitPoolThreads`. | Gauge | `connect_commit_​executor_size​{kubernetes_namespace=~​"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
| **Interpreting the metric**  This metric is a static value. Monitoring it has little value. Refer to it when examining the Active Commits metric. | | |
| `connect_commit_​latency_bucket` | **Commit latency bucket**  Commit latency in milliseconds.  The `connect_commit_​latency_bucket` metric is a histogram that indicates the commit latency. | Histogram | `sum by (phase) (rate(connect_commit_latency_​bucket​{kubernetes_namespace=~​"$namespace"}[5m]))` This metric example presents the Connect commit latency rate metric over the last 5 minutes for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances.  The `connect_commit_​latency_bucket` metric is derived from the `connect_commit_​latency` histogram metric. The `connect_commit_latency` metric also has the `stream` label, therefore the PromQL query can be made to report per stream. |
| **Interpreting the metric**  The commit latency histogram should follow the original baseline values for the most frequently-occurring latency. A bucket of slower than expected latencies and higher than expected occurrences indicates a latency issue, connection delays, or insufficient resources (see CPU, disk and memory usage). In addition, you can watch the stopwatch duration heatmap, `connect_stop_watch_duration_histogram_bucket` metric.  **Log entries**  Review logs to help interpret this metric. Each time an event occurs that increments the metric count, an event status log entry is created. | | |
| `connect_commit_​latency_count` | **Number of completed commits**  This metric is a counter that indicates a running count of the number of commits completed since the last Connect start-up. | Histogram counter | `connect_commit_​latency_count` The `connect_commit_latency_count` metric is derived from the `connect_commit_latency` histogram metric. |
| **Interpreting the metric**  If active commits are being completed, this number will increase. The slope of this graph indicates how busy the commit system is. | | |
| `connect_commit_​queue_size` | **Commit queue** The number of commit jobs currently in the Connect commit queue.  This metric presents the number of commit jobs currently waiting in the Connect Commit Queue. This indicates either   - that more commits are occurring than the system’s executors   can currently handle, or - that multiple commits were sent to the same stream and   further commits to that stream are locked until the active   commit is completed.   A non-zero commit queue is completely normal but there should be periods where it returns to zero. | Gauge | `connect_commit_​queue_size​{kubernetes_namespace=~​"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
| **Interpreting the metric**  A non-zero commit queue is expected, however, the queue should see periods of time where the queue size reaches zero. If the queue never reaches zero, increase CPU core/thread resources and commit workers (`commitPoolThreads`).  If the queue is continuously increasing or “stuck” at the maximum queue size, the system is overwhelmed. This will likely lead to the queue overflowing and commits being lost. This calls for immediate action to:   - tell users to hold off on commits, and - either increase the resources available, or migrate some   projects to another server.   It is also helpful to look at the Is Stream Locked metrics to see if there are any locked streams that could be contributing to the commit queue.  If the queue is hitting the maximum queue size as defined by the `cim.properties` parameter `commitWorkQueueCapacity`, increase the maximum queue size to prevent commits from being lost and failing.  Refer to the section, Changing the number of concurrent commits in the Coverity 2026.6.0 Installation and Upgrade Guide.  Also, for information on memory requirements when you increase the queue size, refer to Sizing a Coverity Connect (cim) pod for optimum performance. | | |
| `connect_is_​accepting_​new_commits` | **Commit gate**  This metric is a boolean gauge which indicates whether or not Connect is currently accepting new commits. | Gauge | `connect_is_accepting_​new_commits​{kubernetes_namespace=~"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
| **Interpreting the metric**  If the Commit Gate is closed (value = 0), Connect is currently not accepting new commits; incoming commits must wait until the gate is open. If the Commit Gate remains closed for an extended amount of time, there might be system issues. To troubleshoot, determine if:   - the commit queue is full, - JVM garbage collection, backups, or skeletonization (snapshot   purging) is in progress, - system resources are within recommended ranges. | | |
| `connect_memory_​used` | Memory used by Connect in the current runtime environment, in bytes. | Gauge | `connect_memory_used​{kubernetes_namespace=​~"$namespace"} / (2^20)` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
