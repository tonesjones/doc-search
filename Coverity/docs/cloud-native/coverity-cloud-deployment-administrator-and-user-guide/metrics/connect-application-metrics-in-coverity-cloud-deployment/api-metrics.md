# API metrics

The following table describes API metrics.

Table 1. API metrics

| Metric | Description | Metric type | Examples: PromQL queries |
| --- | --- | --- | --- |
| `com_coverity_​ces_​web_​filter_​CimInstrumented​Filter_​errors_total` | **Connect HTTP errors count**  This metric is a counter that indicates a running count of the number of HTTP errors since the last Connect start-up. | Counter | `com_coverity_ces_​web_filter_​CimInstrumentedFilter_​errors_total` |
| **Interpreting the metric**  Ideally, this number should be zero, static, and flat. A high error rate (high slope). A high error rate (high slope) indicates that HTTP requests are beyond the capacity of the system. Check the following:   - Connect HTTP status codes - Connect HTTP request latency - CPU and memory usage.   **Log entries**  Each time an event occurs that increments the metric count, a log entry that specifies the event status is created. | | |
| `com_coverity_​ces_​web_​filter_​CimInstrumented​Filter_​requests_count` | **Connect HTTP requests count**  This metric is a counter that indicates a running count of the number of HTTP requests since the last Connect start-up. | Counter | `com_coverity_ces_​web_filter_​CimInstrumentedFilter_​requests_count` |
| **Interpreting the metric**  The slope or rate of view loadings can give of insight into how busy the system is with HTTP requests.  **Log entries**  Each time an event occurs that increments the metric count, a log entry is also created, specifying the event status. | | |
| `com_coverity_​ces_​web_​filter_​CimInstrumented​Filter_​responseCodes_​badRequest_​total` | **Connect HTTP bad requests count**  This metric is a counter that indicates a running count of the number of HTTP bad requests since the last Connect start-up. | Counter | `com_coverity_​ces_​web_​filter_​CimInstrumentedFilter_​responseCodes_​badRequest_​total` |
| **Log entries**  Log entries describe HTTP endpoint, method, and 400 HTTP response codes. | | |
| `com_coverity_​ces_​web_​filter_​CimInstrumented​Filter_​responseCodes_​notFound_​total` | **Connect HTTP notFound count** This metric is a counter that indicates a running count of the number of HTTP 'not found' responses since the last Connect start-up. | Counter | `com_coverity_​ces_​web_​filter_​CimInstrumentedFilter_​responseCodes_​notFound_​total` |
| **Log entries**  Log entries describe HTTP endpoint, method, and 404 HTTP response codes. | | |
| `com_coverity_​ces_​web_​filter_​CimInstrumented​Filter_​responseCodes_​serverError_​total` | **Connect HTTP server errors count** This metric is a counter that indicates a running count of the number of HTTP endpoint server errors since the last Connect start-up. | Counter | `com_coverity_​ces_​web_​filter_​CimInstrumentedFilter_​responseCodes_​serverError_​total` |
| **Log entries**  Log entries describe HTTP endpoint, method, and 500 HTTP response codes. | | |
| `com_coverity_​ces_​web_​filter_​CimInstrumented​Filter_​timeouts_​total` | **Connect HTTP timeouts count** This metric is a counter that indicates a running count of the number of HTTP timeouts since the last Connect start-up. | Counter | `com_coverity_​ces_​web_​filter_​CimInstrumentedFilter_​timeouts_​total` |
| **Log entries**  Log entries describe HTTP endpoint, method, and 408 HTTP response codes. | | |
| `connect_http_​latency_bucket` | **Connect HTTP latency in milliseconds** | Histogram | `sum by (le) (rate(connect_http_latency_bucket​{kubernetes_namespace=~"$namespace", path=~"$connectpath"}[5m]))` This metric example presents the Connect HTTP latency rate metric over the last 5 minutes for a specified namespace and Connect path in a Kubernetes deployment.  `path` refers to the URL path and it is a label available with the `connect_http_latency` metric.  `connectpath` represents a Grafana variable called `connectpath` with the query `"label_values​(connect_http_latency_bucket​{kubernetes_namespace=~"$namespace"}, path)"`.  You might create a variable in the Grafana dashboard to select and view the metric for one of multiple `namespace`/ `path` instances. |
| **Log entries**  Each time an event occurs that increments the metric count, a log entry is created, specifying the event status. | | |
| `connect_http_​latency_count` | **Connect HTTP status codes**  This metric is a histogram counter that can be used to track status codes. | Histogram | `sum by (code) (rate(connect_http_latency_count​{kubernetes_namespace=~"$namespace", path=~"$connectpath"}[5m]))` This metric example presents the latency count metric over the last 5 minutes for a specified namespace and Connect path in a Kubernetes deployment.  `path` refers to the URL path and is a label available with the `connect_http_latency` metric.  `connectpath` represents a Grafana variable called `connectpath` with the query `"label_values​(connect_http_​latency_count​{kubernetes_namespace=~"$namespace"}, path)"`.  You might use a variable drop-down in the Grafana dashboard to select and view the metric for one of multiple `namespace`/ `path` instances. |
| **Interpreting the metric**  HTTP status codes 200, 201 are good. A high number of 400 and 500 level codes can point to system issues. Especially look for 400, 401, 403, and 500 status codes; these can result from an automated script with bad API endpoints, values, authentication or authorization. Because scripts are often started on a scheduled basis, look to see if there is a pattern to the error codes occuring. | | |
| `connect_stop_​watch_​duration_​histogram_​bucket` | **Connect HTTP latency**  This metric is a histogram that indicates HTTP requests latency. | Histogram counter | `sum by (code) (rate(connect_http_latency_count​{kubernetes_namespace=~"$namespace", path=~"$connectpath"}[5m]))` This metric example presents the latency count metric over the last 5 minutes for a specified namespace and Connect path in a Kubernetes deployment.  `path` refers to the URL path and is a label available with the `connect_http_latency` metric.  `connectpath` represents a Grafana variable called `connectpath` with the query `"label_values​(connect_http_​latency_count​{kubernetes_namespace=~"$namespace"}, path)"`.  You might use a variable drop-down in the Grafana dashboard to select and view the metric for one of multiple `namespace`/ `path` instances. |
| **Interpreting the metric**  The HTTP latency histogram, also known as the stopwatch duration heatmap, should follow the baseline values for the most frequently-occurring latency. If the HTTP latency shows a bucket of slower than expected latency and higher than expected occurrence, there is either a latency issue, or resources are insufficient (see CPU, disk and memory usage). | | |
| `connect_stop_​watch_​duration_​histogram_​sum` | **Top resources with latency**  This metric is an indicator of the top X resources with the highest latency.  **Interpreting the metric**  These can help to pin-point endpoints that have higher than expected latency. The number of latencies tracked can be defined in the cim.properties file. | Gauge | `connect_stop_​watch_​duration_​histogram_​sum` |
| `connect_web_​requests_​per_​second` | **Web requests per second**  The number of Web requests per second.  This metric is a gauge which tracks the number of requests made per second. Depending how connect is configured, you might alternatively use Web Socket Requests per second. | Gauge | `connect_web_requests_​per_second​{kubernetes_namespace=~"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might use a variable drop-down in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
| **Interpreting the metric**  Web requests per second should follow the baseline values and will likely have similar peaks and valleys on a weekday by weekday, hour by hour basis. Tracking this over time will see if the load is steady, increasing or decreasing over time.  **Log entries**  Each time an event occurs that increments the metric count, a log entry is created, specifying the event status. | | |
| `connect_ws_​requests_​per_​second` | **Web socket requests per second**  This metric is a gauge which tracks the number of web socket requests made per second.  Note: You might alternatively use web requests per second, depending how connect is configured.  **Interpreting the metric**  The web socket requests per second should follow the baseline values and will likely have similar peaks and valleys on a weekday by weekday, hour by hour basis. Tracking this over time will see if the load is steady, increasing or decreasing over time.  **Log entries**  Each time an event occurs that increments the metric count, a log entry is created, specifying the event status. | | |
| `http_server_​requests_​seconds_​sum` | **Request latency**  This metric is a histogram that tracks server latency.  **Interpreting the metric**  The request latency histogram should follow the baseline values for the most occurring latency. If request latency shows a bucket of slower than expected latency and higher than expected occurrence, there is either a latency issue, or resources are insufficient (see CPU, disk and memory usage). | | |
