# astnode

Every target-code object that Coverity inspects is a node in an *abstract syntax tree*.

For a brief overview of how Coverity uses these syntax trees, see
How does Coverity Analysis work?.

## Properties

Every `astnode` has the following properties:

| Name | Type | Description |
| --- | --- | --- |
| `children` | `list<astnode>` | A list of child nodes that are sub-parts of this code construct |
| `implicit` | `bool` | Indicates whether the node is the result of compiler intervention, as opposed to being explicitly stated in the source code. For example, `if ( x )` in the source code is interpreted as `if ( x != 0 )` by the compiler. The not-equals binary operator and the literal constant zero are *implicit*. |
| `location` | `sourceloc` | The location of this code construct in the source files |
| `macrosExpandedFrom` | `list<macroinfo>` | If the current abstract syntax tree (AST) node comes from the expansion of a macro, or of more than one macro, this field lists those macros. For more information, and a description of `macroInfo` objects, see the "Macro fields" subsection, below. |
| `macroExpansionsPresent` | `list<macroInfo>` | Lists all the macros that were involved in building the current AST. For more information, and a description of `macroInfo` objects, see the "Macro fields" subsection, below. |
| `parent` | `astnode?` | The `astnode` that is the parent of the current node, if there is one. For example, in the case of a `blockstatement`, which contains a list of substatements, the `blockstatement` node is the parent of each statement in the list.  This field is `null` if the current node has no parent. |

The `astnode` elements are further classified as `statement`,
`expression`, `initializer` and
`ctorinit` (constructor initializer),
and `declaration` elements (`declaration` elements
declare symbols).
Various kinds of elements have their own set of properties in addition to the `astnode` properties shown here.

## Macro fields

The `macrosExpandedFrom` and `macroExpansionsPresent` fields let you inspect the macros involved
in building the current abstract syntax tree (AST).

Both of these fields are lists of `macroInfo` objects. A `macroInfo` object is
a record that contains the following fields:

```
macroInfo = record {
    kind : enum(macroKind) {
        `constant`,
        `empty`,
        `function-like`,
        `plain`
    };
    name : string
}
```

kind
:   Indicates how this macro behaves:

    `constant`
    :   The macro immediately expands to a numeric constant.

    `empty`
    :   The macro immediately expands to empty.

    `function-like`
    :   The macro takes arguments, and *does not* immediately expand to empty.

    `plain`
    :   The macro is some other kind of macro.

name
:   The name of the macro.

The `macrosExpandedFrom` field lists the macros that fully generated the current AST node,
while `macroExpansionsPresent` lists macros that were involved in generating the current AST node, but could have generated only a subpart,
or even expanded to empty in between several parts.

So, for example, given the following code:

```
#define M1 1

a + M1
```

... the resulting AST node will be `a + 1`, with `a` and `1` as children.
Both `a + 1` and `1` will have `M1` in `macroExpansionsPresent`.
Only `1` will have `M1` in `macrosExpandedFrom`, while for `a` both lists will be empty.

All the AST nodes generated by the macro at the top level are considered to be expanded by all the macros involved.
For example, if you have these definitions:

```
#define M1 2
#define M2(x) x + M1
```

... then `M2(a)` expands to `a`, `2`, and `a + 2`.
All these nodes will be considered to have expanded from `M2` and `M1`, and all will be listed in the `macrosExpandedFrom` list.

If you have the code `a + M1` this expands to `a + 2`.
Both the `a + 2` and `2` nodes will have `M1` in their `macroExpansionsPresent` list.
