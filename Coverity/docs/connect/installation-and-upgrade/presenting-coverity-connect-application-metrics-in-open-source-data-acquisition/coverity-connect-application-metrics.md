# Coverity Connect application metrics

This document covers application metrics for classic Coverity Connect that are available
in Prometheus format and can add value for customers. Customers configure these metric
in a monitoring system such as New Relic or Grafana.

Coverity Connect application metrics identifies metrics that are available to be
scraped by Prometheus and provided to a monitoring system such as Grafana. Use the
following metrics definitions to view the metrics in a monitoring system such as
Grafana. The examples provide sample Grafana PromQL queries that have been tried in
Grafana dashboards.

Note: Refer to Grafana documentation for information on the PromQL
query language and using PromQL Prometheus queries in Grafana dashboards.

| `connect_active_​commit_count` | **Active commits**  The number of commit jobs currently active in Connect.  The `connect_active_​commit_count` metric is the number of commits currently active and in progress in Connect. The maximum number of active commits is between 0 (no commits in progress) and the number of commit executors or workers as defined by the `cim.properties` parameter `commitPoolThreads`. This together with the commit queue indicates how busy the server is with commits. | Gauge | `connect_active_commit_​count​{kubernetes_​namespace=~"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for `namespace` instances. |
| **Interpreting the metric**  In an ideal system, active commits average 50-75% of the executor size during the active server time, as defined by `commitPoolThreads`. If the average number of active commits is less than half of the executor size, the server might be underutilized.  If active commits are frequently and for sustained periods of time at the max executor size, the system is overutilized. If resources allow, migrate some projects to a server with available resources to better spread the load.  If commit queue is not zero and active commits is less than the maximum executor size, some streams might be locked with commits queued waiting. Look at the stream lock metrics.  If the commit queue is greater than zero and active commits is zero, there is an issue with the queue. Check the logs. | | |

| `connect_commit_​latency_bucket` | **Commit latency bucket**  Commit latency in milliseconds. The `connect_commit_​latency_bucket` metric is derived from the `connect_commit_​latency` histogram metric. | **Interpreting the metric**  The commit latency histogram should follow the original baseline values for the most frequently-occurring latency. Each time an event occurs that increments the metric count, an event status log entry is created. | | |

| **Interpreting the metric**  If active commits are being completed, this number will increase. The slope of this graph indicates how busy the commit system is. | | |
| `connect_commit_​queue_size` | **Commit queue** The number of commit jobs currently in the Connect commit queue.  This metric presents the number of commit jobs currently waiting in the Connect Commit Queue. This indicates either   - that more commits are occurring than the system’s executors   can currently handle, or - that multiple commits were sent to the same stream and   further commits to that stream are locked until the active   commit is completed.   A non-zero commit queue is completely normal but there should be periods where it returns to zero. | Gauge | `connect_commit_​queue_size​{kubernetes_namespace=~​"$namespace"}` This metric example presents metrics for a specified namespace in a Kubernetes deployment. You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
| **Interpreting the metric**  A non-zero commit queue is expected, however, the queue should see periods of time where the queue size reaches zero. If the queue never reaches zero, increase CPU core/thread resources and commit workers (`commitPoolThreads`).  If the queue is continuously increasing or “stuck” at the maximum queue size, the system is overwhelmed. This will likely lead to the queue overflowing and commits being lost. This calls for immediate action to:   - tell users to hold off on commits, and - either increase the resources available, or migrate some   projects to another server.   It is also helpful to look at the Is Stream Locked metrics to see if there are any locked streams that could be contributing to the commit queue.  If the queue is hitting the maximum queue size as defined by the `cim.properties` parameter `commitWorkQueueCapacity`, increase the maximum queue size to prevent commits from being lost and failing.  Refer to the section, Changing the number of concurrent commits in the Coverity 2026.6.0 Installation and Upgrade Guide.  Also, for information on memory requirements when you increase the queue size, refer to Sizing a Coverity Connect (cim) pod for optimum performance. | | |

You might create a Grafana variable in the Grafana dashboard to select and view the metric for one of multiple `namespace` instances. |
| **Interpreting the metric**  If the Commit Gate is closed (value = 0), Connect is currently not accepting new commits; incoming commits must wait until the gate is open.
